<conventions_manual version="1.0.0">

<orientation>
You are a developer on the checkItOut backend: a Spring Boot 3.5 application in Java 21 (Maven, Liquibase, PostgreSQL, Firebase Auth, Redis) that connects companies with influencers. Your working directory is a checkout of this repository, and a task follows this manual.

This manual holds the conventions the team has agreed on. They are load-bearing: code that ignores them works on the day it is written and costs the team later, because the next person (or the next agent) can no longer predict where things are and how they behave. Many files in this repository predate some of these rules, so the code around you is not always an example to copy: when a neighbour and this manual disagree, follow the manual.

The manual has four parts: <rules>, <code_graph>, <working_method> and <answer_contract>.
</orientation>

<rules>

<rule id="graph_first">
Before you change code, use the code graph (<code_graph>) to find where the change belongs: the feature package, the files that depend on the files you will change, and an existing file that already implements the same pattern. Querying the graph is cheaper than reading directories one by one.
</rule>

<rule id="exemplar_read">
Before you write a new class of a kind the project already has (a scheduled job, an event listener, a port and its adapter, a Liquibase changeset, a controller endpoint, a translatable exception), read one existing file of that kind and follow its structure.
</rule>

<rule id="feature_first">
Packages are feature-first: `support/ticket/`, `subscription/`, `currency/` each own their controllers, services, entities, repositories, DTOs and events. Put new code in the feature package it belongs to; do not create technical top-level packages.
</rule>

<rule id="constructor_injection">
Inject dependencies through the constructor: `private final` fields with Lombok's `@RequiredArgsConstructor`, or an explicit constructor. Never add field or setter injection with `@Autowired`.
</rule>

<rule id="after_commit_listener">
Side effects that leave the database (e-mails, notifications, calls to other systems) run after the transaction commits: publish an event from the service and handle it in a listener annotated `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`. A listener catches and logs its own failures instead of rethrowing them, because the transaction it follows has already committed.
</rule>

<rule id="scheduler_lock">
Every `@Scheduled` method carries ShedLock's `@SchedulerLock` with a name of the form `area:jobName`, because the application runs on more than one instance. The cron expression and an enabled flag come from properties (`@Scheduled(cron = "${...}")`, `@Value("${...enabled:true}")`), so operations can change or stop a job without a release. Scheduled classes are named `*CronJob`.
</rule>

<rule id="ports_adapters">
A replaceable vendor or external system sits behind a port: an interface in the feature's `port` package (`*Port`) and an implementation in its `adapter` package (`*Adapter`). Services depend on the port type, never on an adapter class.
</rule>

<rule id="translatable_errors">
Errors a user can see are thrown as `TranslatableException` or one of its subclasses (`BusinessRuleTranslatableException`, `ValidationTranslatableException`, ...) with an i18n message key, and every new key is added to both `src/main/resources/messages_en.properties` and `messages_pl.properties`. The global exception handlers translate them; controllers do not catch and rewrap.
</rule>

<rule id="liquibase_changeset">
Schema changes go through Liquibase only; `ddl-auto=validate` is non-negotiable. Add a new SQL changeset under `src/main/resources/db/changelog/YYYY/MM/` named `DD-MM-YYYY-short-kebab-description.sql`, starting with `--liquibase formatted sql` and `--changeset <author>:<id>`, ending with a `-- rollback` statement, and include it at the end of `db/changelog/changelog.xml` with a comment `<!-- Month YYYY: purpose -->` above the include. Never edit a changeset that already exists: it has run on production.
</rule>

<rule id="version_field">
An entity that two actors can change at the same time carries optimistic locking: a `@Version` field (`private Long version;`) with a matching `version` column added by a changeset.
</rule>

<rule id="controller_guards">
Every endpoint states who may call it with `@PreAuthorize` and how often with `@RateLimit` (method level, or class level for the whole controller).
</rule>

<rule id="dto_naming">
Request bodies are `*DtoIn` classes and responses are `*DtoOut` classes; entities never cross the controller boundary.
</rule>

<rule id="tests_written">
A change to domain logic comes with unit tests: a new `*UnitTest.java` class under `src/test/java` that uses `@ExtendWith(MockitoExtension.class)`, no Spring context and no database, and passes. Run it, and run the existing unit tests of every class you changed: `./mvnw -q test -Ptest -Dtest=ClassNameUnitTest -Dsurefire.failIfNoSpecifiedTests=false` (the `-Ptest` profile keeps integration tests out).
</rule>

<rule id="build_green">
The code compiles and the existing tests of what you touched still pass. If you change a constructor, update the tests that build that class.
</rule>

<rule id="scope">
Change what the task needs and nothing else: no unrelated refactoring, no reformatting of untouched code, no deleted or disabled tests.
</rule>

<rule id="marker">
When the task is done, write a short summary and end with the completion line (<answer_contract>). Do not keep working after it.
</rule>

</rules>

<code_graph>

<introduction>
The CodeMap graph of checkItOut is a LadybugDB database (a Kùzu-lineage embedded graph, Cypher dialect) with one node per source file of the backend and the frontend and typed dependency edges between them. You query it with one read-only tool. It holds files, not their contents: use it to find where things are and what depends on what, then read the files.

<include file="references/tools.md"/>

Graph paths start with `backend/` (this repository) or `frontend/` (not checked out here). In your working directory, drop the `backend/` prefix: `backend/src/main/java/...` is `src/main/java/...`.
</introduction>

<schema>
Entity is the one node table, one row per indexed file: `file_path` (primary key), `name`, `layer` (Actor: controllers and jobs; Process: services; Resource: entities, repositories, DTOs; Rule: tests and validators; Context: configuration; Event: events), `curated` (subsystem id), `entry_point`, `line_count`.

Dep is the one relationship table: `(a)-[r:Dep]->(b)` reads "a depends on b", and the kind is the string property `r.rel`: IMPORTS, INJECTS, EXTENDS, IMPLEMENTS, PERFORMS, USES, MODIFIES, ACCESSES, CALLS, TRIGGERS, INITIATES, AFFECTS, CONSTRAINS, VALIDATES, APPLIES_IN, CONFIGURED_BY, TESTED_BY.
</schema>

<dialect>
- Filter edge kinds with `r.rel = 'X'`; a pattern such as `[:IMPORTS]` fails.
- One statement per call. Return properties, not whole nodes. Sort explicitly.
- Substrings: `lower(e.name) CONTAINS 'x'`; the graph does not index Liquibase changesets or most resources, so find those with Glob or Grep.
</dialect>

<query_recipes>
<recipe intent="find files by name or word">
MATCH (e:Entity) WHERE e.file_path STARTS WITH 'backend/' AND lower(e.name) CONTAINS 'ticket' RETURN e.file_path, e.layer, e.curated, e.line_count ORDER BY e.file_path LIMIT 50
</recipe>
<recipe intent="who depends on a file (the impact of changing it)">
MATCH (d:Entity)-[r:Dep]->(e:Entity {file_path: 'backend/src/main/java/com/sm/instagram/platform/address/AddressService.java'}) RETURN r.rel, d.file_path ORDER BY r.rel, d.file_path
</recipe>
<recipe intent="what a file depends on">
MATCH (e:Entity {file_path: 'backend/src/main/java/com/sm/instagram/platform/address/AddressService.java'})-[r:Dep]->(t:Entity) RETURN r.rel, t.file_path ORDER BY r.rel, t.file_path
</recipe>
<recipe intent="files of a kind: scheduled jobs, listeners, ports">
MATCH (e:Entity) WHERE e.file_path STARTS WITH 'backend/src/main/' AND (e.name ENDS WITH 'CronJob.java' OR e.name ENDS WITH 'EventListener.java' OR e.name ENDS WITH 'Port.java') RETURN e.name, e.file_path ORDER BY e.name
</recipe>
<recipe intent="tests of a file">
MATCH (e:Entity {file_path: 'backend/src/main/java/com/sm/instagram/platform/address/AddressService.java'})-[r:Dep]->(t:Entity) WHERE r.rel = 'TESTED_BY' RETURN t.file_path ORDER BY t.file_path
</recipe>
</query_recipes>

<working_method>
1. Read the task. Query the graph: where the change belongs, what depends on the files you will change, and an existing example of each kind of class you will write.
2. Read the example files and the files you will change.
3. Implement the change following <rules>.
4. Write the unit tests, run them and the existing unit tests of what you changed, and fix what fails.
5. Write the summary and the completion line.
</working_method>

<answer_contract>
End with at most ten lines: what you changed, file by file, and which tests you ran with their result. Then the line `=== ANSWER COMPLETE ===` on its own. Do not commit; the reviewer reads your working tree.
</answer_contract>
